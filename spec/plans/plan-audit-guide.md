# 计划审核规范（Plan Audit Guide）

本规范规定**实施计划在开工前是否要审、谁来审、审什么、怎么写报告、几轮收敛**。

适用对象：`tasks/plans/<topic>/<plan-id>/plan.md`。审核只产出报告，**不修改计划、不写代码**；修改由响应流程负责（`spec/plans/plan-audit-response-guide.md`）。

为什么要有这一环：计划的错误在执行期才暴露，代价是返工与污染主干。审核的价值不是"再读一遍"，而是**在动手前发现验收不可判定、范围漏项、步骤不可执行**这三类会导致返工的问题。

## 版本管理

本规范采用大版本管理方式：

- 初始版本为 `1.0.0`。
- 每次内容变更时，只递增第一个版本号。
- 版本号格式固定为 `主版本号.0.0`。
- 例如：`1.0.0` → `2.0.0` → `3.0.0`。
- 不使用 `1.1.0`、`1.0.1` 等小版本或补丁版本。
- 每次版本更新必须同步更新 `last_updated`。

## 0. 触发：不是每个计划都要审

审核**发生在写实施计划的时候**，方式是选一个入口提示词，不是流程里的一个阶段：

| 入口 | 行为 | 什么时候用 |
| --- | --- | --- |
| `.agents/prompts/feature-plan.prompt.md` · `issue-plan.prompt.md` | 只写计划，不审核，写完即定稿，`Metadata.Audit: none` | 任务简单、路径清楚，第一版就能落地 |
| `.agents/prompts/feature-plan-audited.prompt.md` · `issue-plan-audited.prompt.md` | 写完另起会话或 agent 按本规范审核，再按响应规范调整到收敛 | 命中 0.2 的风险项，或线上事故 |

选档只看 0.2 的命中情况，不看任务大小。**同一份需求/问题不要两份入口混用**：要么一开始就走审核，要么如实记 `none` 并在事后说明。

本规范只管"决定要审之后怎么做"：分档、审核者独立性、审核维度、报告格式、轮次收敛。

### 0.1 三档

| 档位 | 含义 | 轮次预算 | 审核者 |
| --- | --- | --- | --- |
| `none` | 不审（免审） | 0 | — |
| `L1` | 单轮审核 + 响应，必要时一次关闭确认 | ≤ 2 轮 | 另一个人/会话即可 |
| `L2` | 严格审核，必须异构审核 | ≤ 3 轮 | **不同 agent 或不同模型**，且不得与写计划者同一会话 |

### 0.2 判定规则（命中即定档，L2 优先）

**命中任一条即 `L2`：**

1. 鉴权、权限、会话、密钥或凭据处理。
2. 金额、计费、结算、额度、发票。
3. 删除或不可逆数据操作（含批量更新、覆盖写）。
4. **破坏性迁移**：删表/删列/改列类型/加非空无默认列/改主键。
5. 并发、幂等、事务边界、分布式状态、锁。
6. 线上事故修复（hotfix、回滚后的补修）。
7. 对外契约变更：接口字段增删、错误码语义变化、事件格式变化。
8. 涉及外部回调、文件上传、SSRF/反序列化等安全边界。
9. 首次引入第三方依赖，且命中 `spec/dependency/dependency-guide.md` 5.2 的红线。
10. 规模：跨 ≥3 个模块，或「范围-改」清单 ≥15 项。

**未命中 L2 时，命中任一条即 `L1`：**

1. 普通迁移（加表、加可空列、加索引、加约束）。
2. 新增模块、新增对外接口、新增定时任务或 CLI。
3. 依赖主版本升级。
4. 规模：跨 2 个模块，或「范围-改」清单 ≥5 项。
5. 探索性任务（结论可能推翻需求或当前实现）。
6. 该模块近 90 天有 ≥3 个缺陷，或当前无测试覆盖。

**以上都不命中即 `none`（不审）。**

### 0.3 判定要落盘

在 `plan.md` 的 `Metadata` 记录档位与触发理由，一行档位、一行理由：

```md
- Audit: L1
- Audit Trigger: 新增对外接口 + 跨 2 个模块
```

- MUST 每个计划都写 `Audit` 字段：不审写 `none`，审过的写最近一轮档位（`L1` / `L2`）。**不写就看不出这份计划走的哪条路**。
- MUST 触发理由写具体命中的条目，不写"风险较高"。
- MUST 计划范围扩大后重新判定档位；只升不降（已按 L1 开工的，扩到 L2 项就按 L2 补审）。
- MUST NOT 为了省事把 `L2` 写成 `none`。抽查（0.4）会覆盖这一点。

### 0.4 免审抽查

免审不等于免检。`none` 的计划也可能写错，而写错的代价在执行期才出现。

- SHOULD 对上周 `none` 的计划抽检 10%（不少于 2 个），由未参与的人按本规范审一次：报告写 `audits/01-audit.md`，同时把 `Metadata.Audit` 改为 `L1`、`Audit Trigger` 记"抽查"。
- SHOULD 抽检优先命中"文件多却判了 `none`""涉及模块首次改动"这类边界样本。
- MUST 连续两次抽查发现 `none` 误判时，修订 0.2 的阈值并在 `plan.md` 的决策记录说明。

### 0.5 起一次审核：传什么

```text
计划路径：tasks/plans/<topic>/<plan-id>/
报告目录：tasks/plans/<topic>/<plan-id>/audits
报告名：  01-audit                 # 第 2 轮为 02-audit，以此类推
上轮报告：audits/01-audit.md       # 仅复审时提供
```

- MUST `L2` 的审核会话与写计划的会话不共享上下文（新会话 + 不同 agent 或模型）。
- MUST 复审只核 `blocker`、`major` 与上一轮新增问题，不重新全审。每轮全审等于每轮推翻自己，轮次永远收不住。
- SHOULD 出现"判档被反复质疑"或"报告命名错乱"再加 `scripts/plan-audit.sh`（校验 `Audit` 字段、轮次连续性、结论枚举）；现在加属于过度设计。

## 1. 审核者与独立性

- MUST 审核者不是写这份计划的人，也不是同一会话的同一 agent。
- MUST `L2` 使用不同 agent 或不同模型；`L1` 至少换一个会话。
- MUST 审核者只读：可读计划目录、它引用的文件、`spec/`、设计文档；**除新建一份 `audits/NN-audit.md` 外不得写任何文件**（含 `plan.md`、`STATUS.md`、`artifacts/`）。
- MUST 审核者在报告 `Metadata` 写明自己的身份（工具 + 模型 + 会话标识），使"是否独立"可核。
- MUST NOT 由实现者在审核报告里追加"已修复"。关闭由响应报告与下一轮审核表达。

## 2. 审核前准备

按顺序读，不凭印象：

1. `spec/workflow/dev-workflow-guide.md`（流程契约：1:1、Source/Revision、提交粒度）。
2. `spec/plans/plan-writing-guide.md`（目录、字段、状态机）。
3. 计划目录全部文件：`plan.md`、`STATUS.md`、`audits/`（若已有历史轮次）、`artifacts/` 目录清单。
4. 计划里引用的每一条路径、命令、spec 章节，逐个核实存在性（不存在即 blocker 级问题）。
5. 按计划内容选读领域规范：迁移→`alembic-guide`；测试→`spec/testing/`；依赖→`dependency-guide`；前端→`frontend-guide`；流水线→`ci-cd-guide`。

时间盒：`L1` ≤ 15 分钟，`L2` ≤ 30 分钟。超时的未读部分必须写进报告「未覆盖项」，不许假装看过。

## 3. 审核维度（八项，逐项给结论）

| # | 维度 | 检查什么 | 常见缺陷 |
| --- | --- | --- | --- |
| D1 | 定位与结构 | 目录三件套齐全；`plan-id` 合规；`Metadata` 含 `Source`/`Revision`/`Audit`；无横向分类目录 | 报告堆在 `artifacts/`；`Source` 缺失或与 `design.lock` 不一致 |
| D2 | 目标与验收 | 目标一句话结果；验收标准逐条可被第三人判定；有对应命令或可观察结果 | "功能正常"；只写"测试通过"不写跑什么 |
| D3 | 范围 | 「改」清单具体到文件/目录；「不改」写明边界；关键文件无遗漏 | 只写要改的，不写不改的；漏掉配置、迁移、前端类型 |
| D4 | 步骤 | 每步有文件、动作、验证；粒度可单独验证；顺序无倒置；验证命令真实可跑 | "完成后端开发"；步骤里写实现细节；验证写"检查是否正常" |
| D5 | 规范一致性 | 与 `spec/` 不冲突；引用条款存在；技术选型不越界 | 自己发明目录结构；绕过测试或迁移门槛 |
| D6 | 风险与回滚 | 只列会改变做法的风险；回滚步骤可执行；不可回滚项已标注 | 风险写成免责声明；回滚写"恢复代码" |
| D7 | 数据与安全 | 迁移可逆；数据变更可恢复；权限与敏感数据已考虑；写操作幂等 | 破坏性迁移无降级；批量更新无备份 |
| D8 | 流程契约 | 一卡一计划；提交为一次；闭环五条可实现（证据有地方落） | 一个计划盖两张卡；验收证据无处存放 |

判定原则：

- MUST 每条问题都指向**具体位置**（章节、条目、Step、路径），不接受"整体偏弱"。
- MUST 合规性问题引用具体条款（`plan-writing-guide.md` 第 X 章 / `dev-workflow-guide.md` Y 节），不引用"规范精神"。
- MUST NOT 评审风格偏好（措辞、排版）。规范已定的照规范，未定的不管。
- MUST NOT 提出计划范围之外的新需求；要提就明确写"范围外建议，不阻断"。

## 4. 严重度与结论

### 4.1 严重度

| 级别 | 定义 | 例子 |
| --- | --- | --- |
| `blocker` | 不解决就不能开工：会导致返工、数据损坏、验收不可判定，或违反 `spec/` 硬约束 | 验收标准无法判定；破坏性迁移无回滚；步骤缺失关键前置 |
| `major` | 不阻断开工，但执行中大概率返工或产出不可验收 | 范围漏掉迁移文件；验证命令写错；风险未识别 |
| `minor` | 表述、结构、可读性改进 | 术语未定义；Step 描述冗余 |

- MUST `blocker` 必须能回答"不修会发生什么具体后果"。答不出就不是 blocker。
- MUST 单轮 `blocker` 超过 5 条时，直接给 `reject` 并在结论里建议**拆分计划**，不再逐条纠缠细节。

### 4.2 结论

| 结论 | 条件 | 后续 |
| --- | --- | --- |
| `pass` | `blocker = 0` 且 `major = 0` | 可直接开工 |
| `pass-with-changes` | `blocker = 0`，`major ≥ 1` | 必须先走响应流程改计划，改完即可开工，不必复审 |
| `reject` | `blocker ≥ 1` | 必须响应 + 复审（第 5 节） |

- MUST 结论只有这三种，不写"基本通过""建议优化"。
- MUST `pass-with-changes` 时在报告中列出**必须修改的 major 清单**，响应报告逐条对应。

## 5. 轮次与收敛

| 档位 | 最多轮次 | 每轮构成 | 超限处理 |
| --- | --- | --- | --- |
| L1 | 2 | audit → response（→ 关闭确认 audit） | 第 2 轮仍有 blocker：转 L2 或拆计划 |
| L2 | 3 | audit → response → audit … | 第 3 轮仍有 blocker：三选一（见下） |

第 3 轮（L1 为第 2 轮）仍有 `blocker` 时，不许继续下一轮，必须选一条并把理由写进响应报告：

1. **拆计划**：把 blocker 集中的部分拆成独立计划，先做可判定的小单元。
2. **转探索**：改为探索性计划（先做 spike 得出事实），原计划的验收标准暂时挂起。
3. **升级决策**：由人（用户）裁定范围或验收标准，裁定结论写进 `plan.md` 的「决策记录」。

- MUST 轮次硬上限 3（L1 为 2）。不允许"再来一轮看看"。
- MUST 复审只核两件事：上一轮 blocker 是否关闭、本轮是否引入新问题。已 `resolved` 的条目不重开，除非有新证据。
- SHOULD `L2` 的复审换一个与上轮不同的审核者，避免路径依赖。

## 6. 报告

### 6.1 放置与命名

审核报告与计划**同目录**，放 `audits/`：

```text
tasks/plans/<topic>/<plan-id>/
├── plan.md
├── STATUS.md
├── audits/                    # 仅触发审核时创建
│   ├── 01-audit.md            # 第 1 轮审核
│   ├── 01-response.md         # 第 1 轮响应（由响应流程写）
│   ├── 02-audit.md
│   └── 02-response.md
└── artifacts/
```

- MUST 文件名 `NN-audit.md`，`NN` 两位轮次，从 `01` 起，与报告内 `轮次` 一致。
- MUST NOT 放进 `artifacts/`（那里只放命令输出与生成物），也不新建 `reports/`、`reviews/`。
- MUST NOT 用"日期-计划名-audit-NN"这种长名：计划目录已带日期，轮次才是排序依据。
- MUST 每轮一个新文件，禁止覆盖历史轮次。

### 6.2 模板

```md
# 计划审核报告 · <plan-id> · 第 <N> 轮

## Metadata

- 计划：tasks/plans/<topic>/<plan-id>/
- 轮次：<N> / <上限>
- 审核档位：L1（触发项：新增对外接口 + 跨 2 个模块）
- 依据：design@<sha>#<task-id>，Revision <n>
- 审核者：<工具 / 模型 / 会话>
- 时间：2026-11-15 16:40
- 结论：pass | pass-with-changes | reject
- 统计：blocker 0 / major 2 / minor 3
- 上轮报告：N/A（或 audits/01-audit.md）

## 结论摘要

三行内说清：能不能开工、必须先改什么、最大风险是什么。

## 维度判定

| 维度 | 结论 | 说明 |
| --- | --- | --- |
| D1 定位与结构 | pass | 三件套齐全，Source 与 design.lock 一致 |
| D2 目标与验收 | fail | 验收第 3 条不可判定，见 A1-01 |
| ... | ... | ... |

## 问题清单

### A1-01 [blocker] 验收标准第 3 条不可判定

- 位置：plan.md / 验收标准 / 第 3 条
- 现状：「列表加载要快」
- 影响：无法判定完成，最终验证只能靠主观确认
- 要求：改成可测量条件，例如「1000 条数据下首屏接口 P95 < 300ms，用 scripts/bench.sh 输出」
- 依据：plan-writing-guide.md 第 2 章「验收标准」

### A1-02 [major] 范围漏掉迁移文件
...

## 未覆盖项

- 未读 `spec/ci_cd/ci-cd-guide.md`（时间盒耗尽），流水线相关结论未验证

## 复审要求（reject 时填）

- 必须关闭：A1-01、A1-03
- 可延后到开工后：A1-05（minor）
```

规则：

- MUST 问题编号 `A{轮次}-{序号}`（如 `A1-01`），复审时沿用原编号，新问题用本轮前缀。
- MUST 每条含：位置、现状、影响、要求、依据。缺"影响"的条目降为 minor。
- MUST 「未覆盖项」如实写；写"无"也要写。
- SHOULD 「要求」给可执行的替代写法，不只说"需要补充"。

## 7. 禁止事项

- MUST NOT 修改计划、`STATUS.md` 或任何被审文件。审核只产出报告。
- MUST NOT 在报告里写"已修复""已调整"。
- MUST NOT 提出计划范围之外的新功能需求。
- MUST NOT 用风格偏好充当问题（措辞、标题层级、排版）。
- MUST NOT 把"我没看懂"记为 blocker；先按 D2/D4 找不可判定的具体位置。
- MUST NOT 省略「未覆盖项」或伪造已读。
- MUST NOT 超过轮次上限继续审。

## 8. 检查清单

**判定档位时**

- [ ] `Metadata` 已写 `Audit` 与 `Audit Trigger`。
- [ ] 逐条比过 L2 / L1 触发项，没有"大概不严重"的跳过。
- [ ] 范围扩大后重判过档位。

**执行审核时**

- [ ] 已读主流程与计划规范，不是凭记忆。
- [ ] 计划引用的路径、命令、章节逐条核实过。
- [ ] 八个维度都有结论，没有空白。
- [ ] 每条问题有位置、影响、要求、依据。
- [ ] 未覆盖项已如实列出。

**出报告时**

- [ ] 文件在 `audits/NN-audit.md`，轮次与文件名一致。
- [ ] 结论是三种之一，不是模糊表述。
- [ ] `blocker` 都能说清"不修会怎样"。
- [ ] 报告未修改任何被审文件。

## 9. 与其他规范的关系

| 规范 | 关系 |

| `spec/plans/plan-writing-guide.md` | 计划的目录、字段、状态机；本规范审的就是它 |

| `spec/testing/`、`spec/dependency/`、`spec/alembic/` | D5/D7 判定时引用其条款，不在本规范复述 |
