# 计划审核响应规范（Plan Audit Response Guide）

本规范规定**拿到审核报告之后怎么处置、怎么改计划、怎么写响应报告**。

与 `spec/plans/plan-audit-guide.md` 成对使用：审核报告只提出问题，本规范负责逐条闭环。**响应阶段改的是计划文档，不是代码。**

> 计划还在 `Planned`，代码尚未动。若已经开始实施才收到审核意见，先回退到计划层判断：改计划能解决的改计划；已写代码的按 `spec/testing/regression-testing-guide.md` 当缺陷处理。

## 版本管理

本规范采用大版本管理方式：

- 初始版本为 `1.0.0`。
- 每次内容变更时，只递增第一个版本号。
- 版本号格式固定为 `主版本号.0.0`。
- 例如：`1.0.0` → `2.0.0` → `3.0.0`。
- 不使用 `1.1.0`、`1.0.1` 等小版本或补丁版本。
- 每次版本更新必须同步更新 `last_updated`。

## 0. 什么时候要写响应

| 审核结论 | 是否要响应 | 响应后 |
| --- | --- | --- |
| `pass` | 不需要 | 直接开工 |
| `pass-with-changes` | **要**，逐条处置 major 与 minor | 改完即可开工，不必复审 |
| `reject` | **要**，逐条处置全部 blocker | 改完请求复审（下一轮 audit） |
| 免审抽查发现问题 | 按 `reject` 处理 | 同上 |

- MUST 一份响应报告对应一份审核报告，文件轮次一致：`audits/NN-audit.md` ↔ `audits/NN-response.md`。
- MUST NOT 一对多（一份响应覆盖两轮审核）或漏写（有 audit 无 response）。
- MUST 同一轮内先核查、再修改、最后写报告，顺序不可颠倒。

---

## 1. 响应者与边界

- MUST 响应者是计划的作者（写 `plan.md` 的人），不是审核者。
- MUST 只改 `plan.md`（必要时含计划目录结构），**不改代码、不改 `spec/`、不改设计仓**。
- MUST 审核意见指向设计文档本身有问题时，不在项目仓"顺手改设计"，而是 `STATUS.md` 转 `Blocked` 并在响应里写"待设计仓修正"，附设计侧 issue 链接。
- MUST NOT 在 `plan.md` 里删除或淡化审核已指出的问题；改动必须可对照响应报告追到具体位置。

---

## 2. 逐条处置

每条 finding 只能落到四种处置之一：

| 处置 | 含义 | 必须给什么 |
| --- | --- | --- |
| `accept` | 意见成立，已改计划 | 改在哪个章节 / 哪个 Step（写具体位置） |
| `partial` | 部分成立，只改成立的部分 | 改了哪部分 + 未改部分的理由 |
| `reject` | 不成立或与规范冲突 | **证据**：引用 spec 条款、文件行号、或事实（如命令输出） |
| `defer` | 成立但本次不做 | 为什么可以延后 + 落到「遗留问题」+ 后续计划标识 |

按严重度限定处置：

| 严重度 | 允许的处置 |
| --- | --- |
| `blocker` | `accept` 或 `reject`（带证据）。**不允许 `defer`** |
| `major` | 四种都允许；`defer` 必须写进「遗留问题」并给时限 |
| `minor` | `accept` 或 `defer`，不阻断开工 |

- MUST `reject` 必须指向可核查的依据，不接受"我认为不需要""这样也可以"。
- MUST `partial` 说明未采纳部分的技术理由，不写"视情况而定"。
- MUST NOT 把 `blocker` 写成 `defer` 来绕过复审。
- MUST NOT 为通过审核而放宽验收标准：可以把"列表要快"改成"P95 < 300ms"，不可以把"P95 < 300ms"改成"响应及时"。

## 3. 改计划时改哪里

审核意见与修改位置不是随意的，按下表对应：

| 审核指出的问题 | 改 `plan.md` 的哪一节 | 注意 |
| --- | --- | --- |
| 验收不可判定 | 「验收标准」+「最终验证」的预期 | 改成可执行命令或可观察结果；判定条件不得放宽 |
| 范围漏项 | 「范围 - 改」清单 | 补文件/目录；同时补「不改」边界 |
| 步骤不可执行 / 粒度太粗 | 「步骤」 | 拆到"一步一验证"；补 `验证` 命令 |
| 缺前置条件 | 「前置条件」 | 写清依赖的计划、环境、权限、数据 |
| 风险缺失 | 「风险」+「回滚」 | 只写会改变做法的风险；回滚要能执行 |
| 与 spec 冲突 | 做法本身 | 改做法；确需例外时写进「决策记录」并引用条款 |
| 流程契约不符（1:1、提交粒度） | 「Metadata」+ 提交说明 | `Source` 与 `design.lock` 对齐 |
| 范围外建议 | 「遗留问题」 | 不改范围，只登记 |

- MUST 只改被指出的部分与它连带的字段，不趁机重写全文（重写会掩盖 diff，让复审无法核对）。
- MUST 每处改动在响应报告的「计划变更摘要」里各占一行，写"章节 → 改了什么"。
- MUST `plan.md` 的时间字段更新为真实时间；禁止编造。
- SHOULD 改动超过计划篇幅 30% 时，先考虑审核建议的"拆分计划"，而不是把一份计划改成两份的内容。

## 4. 响应报告

### 4.1 放置与命名

与审核报告同目录、同轮次：

```text
tasks/plans/<topic>/<plan-id>/audits/
├── 01-audit.md
├── 01-response.md      # 对应第 1 轮审核
├── 02-audit.md
└── 02-response.md
```

- MUST 文件名 `NN-response.md`，`NN` 与对应审核报告一致。
- MUST NOT 覆盖历史轮次；每轮一份新文件。
- MUST NOT 放进 `artifacts/`。

### 4.2 模板

```md
# 审核响应报告 · <plan-id> · 第 <N> 轮

## Metadata

- 计划：tasks/plans/<topic>/<plan-id>/
- 对应审核：audits/<N>-audit.md
- 轮次：<N> / <上限>
- 响应者：<工具 / 模型 / 会话>
- 时间：2026-11-15 17:05
- 审核结论：reject（blocker 2 / major 3 / minor 1）
- 处置统计：accept 4 / partial 1 / reject 1 / defer 0
- 结论：ready-for-reaudit | ready-to-start | escalate

## 逐条处置

| 编号 | 意见摘要 | 处置 | 改动位置 | 依据 / 说明 |
| --- | --- | --- | --- | --- |
| A1-01 | 验收第 3 条不可判定 | accept | 验收标准 第 3 条 | 改为 P95 < 300ms + scripts/bench.sh |
| A1-02 | 范围漏掉迁移文件 | accept | 范围 - 改 | 补 backend/alembic/versions/ |
| A1-03 | 建议增加导出功能 | reject | — | 范围外需求，见遗留 Q-01；依据 workflow 2.2 |
| A1-04 | 风险未覆盖并发 | partial | 风险 第 2 条 | 已补锁竞争；分布式锁不在本计划范围 |

## 计划变更摘要

- 验收标准：第 3 条改为可测量条件
- 范围：新增迁移目录；「不改」补前端展示层
- 步骤：Step 3 拆为 3a/3b，各带验证命令
- 决策记录：新增一条"不做导出"，写明原因

## 未处置项与风险

- A1-04 的分布式锁：已记入「遗留问题」，建议后续单独计划
- 已按审核要求收紧验收，未放宽任何原判定条件

## 结论

可进入复审 / 可直接开工。若可开工，说明还需谁确认。
```

规则：

- MUST 处置表覆盖审核报告中的**每一条** finding，编号与顺序不变（禁止重新编号）。
- MUST 处置表与 `plan.md` 的实际改动一致；正文改了但表里没有，视为响应不完整。
- MUST 「未处置项与风险」写明 `defer` / `partial` 的残留，不能空着。
- MUST 结论是三选一，不写"基本处理完毕"。

## 5. 轮次与收敛

轮次上限与超限处理见 `spec/plans/plan-audit-guide.md` 第 5 节。响应侧的动作是：

| 情形 | 响应结论 | 下一步 |
| --- | --- | --- |
| 所有 blocker 已 `accept` 并改完 | `ready-for-reaudit` | 请求下一轮审核（只核 blocker 与新增问题） |
| 只有 blocker 被 `reject`（有证据） | `ready-for-reaudit` | 复审时由审核者裁定证据是否成立 |
| `pass-with-changes` 的 major 全部处置 | `ready-to-start` | 直接开工，不必复审 |
| 已到上限仍有 blocker | `escalate` | 必须选一条出路（见下） |

到上限时三选一，并把选择写进响应报告与 `plan.md` 的「决策记录」：

1. **拆计划**：blocker 集中的部分拆成新计划（新 `plan-id`），原计划缩范围后开工。
2. **转探索**：`plan.md` 改为探索性计划（目标改为"得出事实"，验收改为"结论 + 证据"），原需求另开计划。
3. **升级决策**：请用户裁定范围或验收标准；裁定结果原文写入「决策记录」。

- MUST 第 3 轮（L1 为第 2 轮）结束时必须给出上述之一，不允许"再改一轮"。
- MUST 拆分后原计划与新计划互相在「前置条件」/「遗留问题」里引用，保持可追溯。

---

## 6. 禁止事项

- MUST NOT 改代码。响应阶段只动计划。
- MUST NOT 改审核报告（包括"补充说明""已修复"）。
- MUST NOT 删除、合并或重排审核意见的编号。
- MUST NOT 用放宽验收标准、缩小范围却不说明、把 blocker 降级的方式换取通过。
- MUST NOT 在 `plan.md` 里写"按审核意见已修改"而不写改了哪里（要可核对）。
- MUST NOT 跳过核查直接照改：意见不成立时要敢于 `reject` 并给证据。
- MUST NOT 超过轮次上限继续循环。

## 7. 检查清单

**核查阶段**

- [ ] 审核报告每一条都读了，编号记全。
- [ ] 每条都判断过"在当前 `plan.md` 里是否成立"，有证据。
- [ ] 设计侧问题已识别，未在项目仓改设计文档。

**修改阶段**

- [ ] 只改被指出的部分与连带字段，没有趁机重写。
- [ ] 验收标准只收紧或改为可判定，没有放宽。
- [ ] `Source` / `Revision` 与 `design.lock` 仍一致。
- [ ] 时间字段真实，未编造。

**出报告阶段**

- [ ] `audits/NN-response.md` 与对应 audit 同轮次。
- [ ] 处置表覆盖全部 finding，编号未变。
- [ ] 「计划变更摘要」与 `plan.md` 实际改动一致。
- [ ] 结论是三选一；到上限时已给出拆计划 / 转探索 / 升级决策之一。
